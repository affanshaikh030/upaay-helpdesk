# Helpdesk (AI-Powered Ticket Management System)

Support tickets are created from emails, then classified, summarized and answered with AI. Agents manage them in a dashboard.

Source-of-truth docs (read these first):
- `project-scope.md`: problem, features, statuses, categories, roles
- `tech-stack.md`: chosen technologies
- `implementation-plan.md`: phased checklist; tick items off as they are done

## Stack
- **Runtime & package manager:** Bun. Use `bun install`, `bun add`, `bun run`. Do not use npm, yarn or pnpm.
- **Monorepo:** Bun workspaces: `client/` (React + Vite + TypeScript), `server/` (Express + TypeScript), `core/` (`@helpdesk/core`: Zod schemas and types shared by both, shipped as TypeScript source with no build step)
- **Auth:** database sessions (email and password), with a seed script that creates the first admin from environment variables
- **Planned:** Tailwind CSS, React Router, PostgreSQL + Prisma, Zod, Claude API (Anthropic SDK), SendGrid/Mailgun, Docker, Railway

## Commands
- Server: `cd server && bun run dev` (http://localhost:3000, health check at `/api/health`); `bun run typecheck`; `bun run test` (Vitest unit tests with the database, queue and AI SDK mocked, no server or key needed)
- Client: `cd client && bun run dev` (Vite, default port 5173, falls back if taken); `bun run build`; `bun run lint`; `bun run test` (component tests, see below)
- The Vite dev server proxies `/api` to `http://localhost:3000`. Call the API with relative paths (`/api/...`), not absolute URLs.
- **Client data fetching:** use `axios` for HTTP requests (never `fetch`) and TanStack Query (`@tanstack/react-query`) for server state. Wrap each query in a hook under `client/src/hooks/` (see `use-users.ts`: `useQuery` with an exported query key, passing the `signal` from `queryFn` to axios) and use `useMutation` for writes, invalidating the related query key on success. Don't fetch in `useEffect` or keep server data in `useState`. The `QueryClient` is set up in `client/src/main.tsx` with retries off. Better Auth's `authClient` keeps making its own auth requests.

## Authentication
- **Library:** Better Auth (`better-auth`) with the Prisma adapter and database sessions (cookies). Server config: `server/src/auth.ts`, mounted at `/api/auth/*` in `server/src/index.ts` (before `express.json()`). Client: `authClient` in `client/src/lib/auth-client.ts` (`useSession`, `signIn.email`, `signOut`).
- **Email and password only; sign-up is disabled** (`disableSignUp: true`, and `/api/auth/sign-up/*` returns 404). Users are created by the seed script or an admin, never self-service. **Passwords must be at least 12 characters** (`MIN_PASSWORD_LENGTH` in `core/src/users.ts`, used by `createUserSchema`/`updateUserSchema` and by Better Auth's `minPasswordLength` in `auth.ts`; the seed and reset scripts keep their own 12). The minimum applies only when a password is set or changed: signing in is never checked against it, so older shorter passwords keep working.
- **Roles:** `user.role` is a server-owned additional field (`input: false`, default `AGENT`); the seeded admin gets `ADMIN`. Never accept `role` from client input.
- **Use the `Role` enum, never role string literals** (`"ADMIN"`, `'AGENT'`, `'ADMIN' | 'AGENT'`), including in tests:
  - **Client:** `import { Role } from '@helpdesk/core'` and use `Role.ADMIN` / `Role.AGENT` in comparisons (`session.user.role === Role.ADMIN`) and test fixtures. Type a role as `Role` (e.g. `role: Role` in the `User` type), not a hand-written union.
  - **Server:** `import { Role } from './generated/prisma/enums'` (relative path to `server/src/generated/prisma/enums`), e.g. `requireRole(Role.ADMIN)` and `role: Role.AGENT`.
  - `prisma/schema.prisma` is the source of truth; `core/src/roles.ts` mirrors it for the client, and `server/src/enum-sync.ts` fails typecheck if the two differ (it also covers `TicketStatus` and `TicketCategory`, mirrored in `core/src/tickets.ts`). When adding a value to any of these enums, update the Prisma enum and the `core/` mirror together. In the client use `TicketStatus.OPEN`, `TicketCategory.REFUND_REQUEST` etc. from `@helpdesk/core`, not string literals.
- **First admin:** `cd server && bun run seed` reads `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` (min 12 characters, no placeholders), `SEED_ADMIN_NAME` (optional). Idempotent: an existing ADMIN is a no-op; an existing non-admin with that email is only promoted if `SEED_PROMOTE_EXISTING=true`, otherwise the script exits with an error.
- **Reset a password:** the seed never changes an existing user's password. Use `cd server && NEW_PASSWORD='...' bun run reset-password <email>` (`server/scripts/reset-password.ts`): hashes with Better Auth, updates only that user's credential account, keeps sessions, never prints the password. Same 12-character minimum as the seed.
- **Env vars** (see `.env.example`): `DATABASE_URL`, `BETTER_AUTH_SECRET` (required, 32+ characters, not the `.env.example` placeholder; `auth.ts` throws at startup otherwise), `BETTER_AUTH_URL` (server origin; **required when `NODE_ENV=production`**, `requireBaseUrl` in `server/src/base-url.ts` stops the server at startup without it), `INBOUND_EMAIL_SECRET` (optional; enables the inbound email webhook, see below), `TRUSTED_ORIGINS` (comma-separated browser origins, default `http://localhost:5173`; add the deployed client origin), `SENTRY_DSN` (optional; enables server error monitoring, see below), `AUTO_RESOLVE_SHADOW_MODE` (optional; AI auto-resolve only records what it would do unless this is exactly `false`, see "Knowledge base and AI auto-resolve").
- **Protecting routes:** server: everything under `/api` after `/api/health` goes through `requireAuth` (`server/src/middleware/auth.ts`, 401 without a session, sets `res.locals.user`/`session`); add `requireRole("ADMIN")` per route for admin-only endpoints (403 otherwise). Never rely on client-side guards (`AdminRoute`) for authorization. Client: `Layout` redirects to `/login` without a session; `LoginPage` redirects to `/` with one.
- **Rate limiting of the AI routes and the inbound webhook** (`express-rate-limit`, `server/src/rate-limit.ts`, in-memory so per process, fine for the single replica; always on, also in dev): polish, summarise and re-analyse share a counter of 20 per minute and 200 per hour **per signed-in user**; `POST /api/inbound/email` allows 120 per minute **per client address**, checked before the secret. Over the limit gives 429 `{ error }`. `index.ts` sets Express `trust proxy` to 1 when `TRUST_PROXY_HEADERS=true`, so on Railway the limiter sees real client addresses instead of one shared proxy address. Inbound email strings have NUL characters and lone surrogates removed before validation (PostgreSQL can't store them).
- **Rate limiting (sign-in, Better Auth):** enabled only when `NODE_ENV=production` (off in dev and tests) in `auth.ts`, with database storage (`rateLimit` table); `/sign-in/email` is limited to 5 per 60s per IP, others 100 per 60s. Behind a reverse proxy set `TRUST_PROXY_HEADERS=true` so real client IPs are used. `NODE_ENV=production` must be set in the deployment or there is no limiting at all.

## Inbound email (tickets)
- `POST /api/inbound/email` (`server/src/routes/inbound-email.ts`) turns a support email into a `Ticket` (status `OPEN`; category stays empty until AI assigns one). Ticket ids are auto-incrementing integers and `category` is nullable with no default. It is **provider-neutral**: it takes JSON validated by `inboundEmailSchema` in `core/src/tickets.ts` (`from`, `fromName` (required), `subject?`, `text`, `messageId?`). SendGrid/Mailgun adapters will translate their payloads into it; no provider is set up yet.
- **No session; guarded by `INBOUND_EMAIL_SECRET`** sent as the `x-inbound-secret` header (constant-time compare, 401 otherwise). Unset disables the endpoint (404); a placeholder or value under 32 characters makes the server fail at startup. It is mounted in `server/src/index.ts` before `express.json()` and `requireAuth` and parses its own body (1mb limit).
- **Optional `bodyHtml`** (max 100,000 characters) is stored on the ticket as given. It is returned only by `GET /api/tickets/:id`, never by the list, and the client sanitizes it with `sanitizeEmailHtml` (`client/src/lib/sanitize-html.ts`, DOMPurify with a tag allow-list: no forms, inputs, buttons, styles, images, `class`/`id`/`style` attributes; links open in a new tab with `rel="noopener noreferrer"`) before rendering; without it the plain text `body` is shown.
- **Auto-classify (pg-boss):** after the ticket is created the route enqueues a `classify-ticket` job (`enqueueClassify` in `server/src/queue.ts`, payload `{ ticketId, autoResolve: true }` for a new email; re-analysis omits the flag, and the worker queues auto-resolve only for flagged jobs, after classification succeeded); an enqueue failure is logged and never fails the webhook. The worker calls `classifyTicket` (`server/src/classify-ticket.ts`), which loads the ticket and asks the same Gemini model (`aiModel` in `server/src/ai.ts`) in **one structured call** for `{ category, sentiment, priority }` (`TicketCategory`, `TicketSentiment` POSITIVE/NEUTRAL/NEGATIVE, `TicketPriority` LOW/MEDIUM/HIGH/URGENT). Each field is written only while it is still null (one conditional `updateMany` per field), so an agent's value is never overwritten; a ticket that already has all three is skipped, and an older one that only lacks sentiment and priority keeps its category. `sentiment` and `priority` are nullable columns (additive migration): tickets created before they existed stay null and show a dash. The queue name stays `classify-ticket` so queued jobs are never orphaned. It throws on any failure, and the queue retries 4 times with exponential backoff (30s base, 10m cap). Runs only for newly created tickets (not the `messageId` duplicate path). pg-boss keeps its tables in its own `pgboss` schema in the same database; `startQueue()` runs before `listen`, and SIGINT/SIGTERM stop the HTTP server, wait for the active job (20s), close the queue and disconnect Prisma. The worker is registered **only when `GOOGLE_GENERATIVE_AI_API_KEY` is set**: without it (e.g. the e2e API) jobs are still enqueued but never processed, so Gemini is never called and they run once a key is configured.
- **Auto-resolve (pg-boss):** the `auto-resolve-ticket` job (same retry options and the same "only when `GOOGLE_GENERATIVE_AI_API_KEY` is set" worker rule) is queued by the classify worker, not by the webhook, so priority and sentiment always exist first; if classification fails for good, auto-resolve never runs (fails closed). `autoResolveTicket` (`server/src/auto-resolve-ticket.ts`) answers only from knowledge base articles and is in **shadow mode by default**: see "Knowledge base and AI auto-resolve" below for the gates, shadow mode and the audit table. When it does resolve, one transaction sets the ticket `RESOLVED` with `resolvedByAi = true` and adds the answer as a `Reply` (`AGENT`, no author, `sourceArticleId` set; the thread shows "AI assistant"). The answer is only stored: there is no outbound email yet. **`GET /api/tickets` hides `resolvedByAi` tickets by default** (also from `total`; see the `aiResolved` filter); they are still reachable by id.
- **Idempotent on `messageId`:** a repeat of a stored Message-ID returns `200` with the existing ticket id instead of creating a duplicate. Without a `messageId` every call creates a ticket. There is no threading yet: every email is a new ticket.

## Knowledge base and AI auto-resolve
- **Replaces `server/knowledge-base.md`**, which is deleted and no longer read. The articles live in the database and admins manage them; **the knowledge base starts empty after the migration**, so until articles are entered every ticket is recorded as `NO_RELEVANT_ARTICLE`. The old file's text stays in git history for copying. Its "Escalation Rules" section was policy, not an answer, and became the code in `server/src/escalation.ts` and the prompt.
- **Data** (additive migration `add_knowledge_base_and_auto_resolve_attempts`): `KnowledgeArticle` (`title`, `content`, optional `language` EN/HI/GU that is informational only, timestamps, and `searchVector`, a Postgres **generated** `tsvector` column: title weight A, content weight B, with a GIN index; Prisma declares it as `Unsupported("tsvector")` and the generated-column SQL was written by hand in the migration, so never regenerate that migration); `Reply.sourceArticleId` (nullable, `SetNull` when the article is deleted); `AutoResolveAttempt` (below). The enums `KnowledgeLanguage`, `AutoResolveDecision` and `AutoResolveReason` are mirrored in `core/src/knowledge.ts` and checked by `server/src/enum-sync.ts`.
- **Admin API** (`server/src/routes/knowledge.ts`, mounted at `/api/knowledge`, router-level `requireRole(Role.ADMIN)`, 403 for agents): `GET /`, `POST /`, `PATCH /:id` (partial), `DELETE /:id` (hard delete; replies keep their text and lose the source link) and `GET /attempts`. Schemas in `core/src/knowledge.ts`: `title` 1-200 characters (`KNOWLEDGE_TITLE_MAX`), `content` 1-20,000 (`KNOWLEDGE_CONTENT_MAX`), `language` nullable.
- **Retrieval** (`server/src/knowledge-search.ts`): Postgres full-text search, no pgvector and no extra service. `buildSearchQuery` turns the ticket subject and body into at most 12 distinct lowercase words (letters, digits and combining marks only, stop words and bare numbers dropped, subject first) joined with ` | `, so no tsquery operator can survive; it is passed as a bound parameter to `to_tsquery('english', $1)` (never string-built SQL). Rank is `ts_rank_cd(..., 32)`, normalised to 0..1; the top `KNOWLEDGE_RESULT_LIMIT` (5) are returned, and only those at or above `MIN_RETRIEVAL_RANK` (0.3) go to the model. 0.3 is a starting guess: tune it from the `topRank` that every attempt records. The vector is English-stemmed, so a Hindi or Gujarati ticket only matches articles that contain the same words, and never an English article: those tickets escalate to a human.
- **Gate order** in `autoResolveTicket`, cheapest first, each early exit writing one `AutoResolveAttempt` and leaving the ticket to a human: (0) a ticket that already has an attempt is skipped; (1) not open, already AI-resolved or an agent replied (no row); (2) not classified (category, priority or sentiment null), `NOT_CLASSIFIED`; (3) priority `URGENT`; (4) sentiment `NEGATIVE`; (5) category `REFUND_REQUEST` (the purchase date is unknown, so "outside the 30-day window" can't be checked); (6) escalation wording, `ESCALATION_WORDING`; (7) best search rank under the minimum, `NO_RELEVANT_ARTICLE` (the model is not called); (8) the model call, which must return `resolvable`, `confidence` and `citedArticleIds`, then: not resolvable or no reply `MODEL_DECLINED`, confidence under `MIN_CONFIDENCE` (0.8) `LOW_CONFIDENCE`, and no cited id or one that was not among the supplied articles `INVALID_CITATION`. Gates 2-5 read the ticket as it is now, so an agent's override counts.
- **Escalation wording** (`server/src/escalation.ts`, pure `detectEscalation`): legal (lawyer, sue, court, legal action...), chargeback or dispute, and security (hacked, breach, fraud, phishing...), in English plus Hindi and Gujarati terms (the latter two need a native speaker's review). English terms match whole words only; Hindi and Gujarati match as substrings. It is a safety net that errs towards escalating and can be evaded by misspelling; the prompt repeats the rules. Add a term to `ESCALATION_TERMS` (a test checks every listed term matches its own category and none is listed twice).
- **Shadow mode** (`isShadowMode()`, read on every job): controlled by the environment variable **`AUTO_RESOLVE_SHADOW_MODE`**, and **`false` is the only value that turns it off**. Unset, empty, `False`, `0`, `no` or a typo all keep it on, so a mistake can never make the AI live. In shadow mode the whole pipeline (search, model call, every gate) runs and is recorded with `decision: RESOLVE`, `acted: false` and the `draftReply`, but no ticket, reply or status changes. Review the results on the Knowledge page, then set the variable to `false` to go live (a Railway variable change, no code change).
- **Live path:** one transaction checks the cited articles still exist, does a conditional `updateMany` (still `OPEN`, not AI-resolved, no replies, and not `URGENT`, `NEGATIVE` or `REFUND_REQUEST`), adds the reply with `sourceArticleId` (the first cited article) and writes the attempt with `acted: true`. If an agent got there first or an article was deleted it writes `TICKET_CHANGED` and changes nothing.
- **`AutoResolveAttempt`** (audit table, one row per ticket, `ticketId` unique so a retried or duplicate job records nothing more): `decision` (`RESOLVE`/`ESCALATE`), `reason`, `suppliedArticleIds` and `citedArticleIds` (plain ids with no foreign key, so the trail survives an article deletion), `topRank`, `modelResolvable`, `confidence`, `draftReply` (only when the decision is `RESOLVE`), `acted`, `shadow`, `createdAt`.
- **Client:** `/knowledge` (`KnowledgePage`, admin only: behind `AdminRoute`, a navbar link for admins, 403 state like the Users page) lists, creates, edits and deletes articles with the shared length limits, and below them shows the "AI auto-resolve results" table fed by `GET /api/knowledge/attempts` (ticket subject, decision, shadow or live, reason, top rank, confidence, draft reply, cited article title or "Deleted"; paged). The ticket list has an **AI-resolved** filter (`aiResolved`: `exclude`, the default that hides them and sends no parameter, `only`, or `include`) and marks AI-resolved rows with a sparkles icon. Under an AI reply the ticket detail shows **"Based on: <article title>"** from `reply.sourceArticle`, as plain text (never a link, since agents can't open the Knowledge page) and nothing at all once the article is deleted. Strings are in the i18n dictionary (en, hi, gu).
- **Tests:** server `bun run test` covers every gate and its order, citation checks, shadow mode and the live transaction, the job chaining, the search query builder (hostile input) and the knowledge routes, all with the database, queue and Gemini mocked; the SQL itself is only exercised against a real Postgres when run by hand.

## Tickets
- `GET /api/tickets` (`server/src/routes/tickets.ts`): any signed-in user, newest first (`createdAt` desc, then `id` desc), without the body. Client: `/tickets` page (`TicketsPage`, `TicketsTable`, `useTickets`), linked from the navbar for everyone. The list also filters (`?status=&category=&priority=&sentiment=&aiResolved=&search=`, where `UNCATEGORIZED` / `UNSET` mean "not set yet", and `aiResolved` is `exclude` (the default: AI-resolved tickets stay hidden), `only` or `include`), sorts (`sortBy` includes `priority` and `sentiment`, nulls last; the Prisma enum declaration order is the sort order, so priority ascends low to urgent and sentiment descending puts NEGATIVE first) and pages.
- **Priority and sentiment:** shown as a badge and an icon in the list (`TicketTags`), in the ticket header and as editable selects in the sidebar: `PATCH /api/tickets/:id` accepts `priority` and `sentiment` (null clears), so agents can override the AI. Labels live in the i18n dictionary (en, hi, gu), unlike status and category.
- **Re-analyse (admin only):** `POST /api/tickets/reanalyse` (`reanalyseTicketsSchema`, `server/src/reanalyse.ts`) queues the classify job again for tickets whose `sentiment` or `priority` is still null: optional `{ ticketIds }`, otherwise the oldest untagged ones, at most `REANALYSE_LIMIT` (10) per request. It uses `enqueueClassifyThrottled` (one job per ticket per 5 minutes, so repeated clicks cannot pile up Gemini calls), answers `{ queued, remaining }`, and 503 without a Gemini key. Use it from the "Analyse with AI" button in the sidebar, the "Analyse untagged tickets" button on the list (`AnalyseButton`), or any API client with an admin session. No script is involved.

- **Dashboard:** `/` (`HomePage`, `useStats`) shows `GET /api/stats` (`server/src/routes/stats.ts`, any signed-in user): total, open, resolved by AI, % resolved by AI and average resolution time, plus a bar chart of new tickets per day over the last 30 UTC days (`ticketsPerDay`, zero-filled, hand-built SVG in `TicketsPerDayChart`, no chart library). Unlike the list, the counts **include AI-resolved tickets**. `Ticket.resolvedAt` is set when a ticket becomes `RESOLVED` (the PATCH route or the auto-resolve job), kept on `CLOSED` and cleared on reopen; the average is `resolvedAt - createdAt` over tickets that have one. The migration backfilled old resolved/closed tickets with `updatedAt`, so their times are approximate. The stats query key sits under the `tickets` key, so ticket mutations refresh it.

- **Suggested reply:** `GET /api/tickets/:id/suggested-reply` (any signed-in user, read only) returns `{ suggestion }` from the ticket's `AutoResolveAttempt`: `{ draftReply, confidence, article: { id, title } | null }`, or `null` when there is no `RESOLVE` draft or the ticket already has a reply. It works in shadow mode and needs no schema. `SuggestedReply` (in `ReplyThread`) shows it only while the ticket has no replies, labelled "AI-generated draft" with "Based on: <title>"; "Use this reply" only fills the Reply textarea (the agent still presses Send reply) and "Dismiss" hides it for the page view.

- **Polish reply:** `POST /api/tickets/:id/replies/polish` (body `polishReplySchema` in `core`: `subject`, `customerName`, `customerMessage`, `draft`) returns `{ body }` improved by `gemini-3.5-flash-lite` (`gemini-2.5-flash-lite` now returns 404 for new users) via the Vercel AI SDK (`ai`, `@ai-sdk/google`) and saves nothing. The key is `GOOGLE_GENERATIVE_AI_API_KEY` in `server/.env` only (never the client); unset gives 503. The "Polish" button in `ReplyThread` replaces the textarea with the result.

- **Summarise:** `POST /api/tickets/:id/summary` (no body) loads the ticket and its replies from the database and returns `{ summary }` from the same Gemini model, regenerated on every call and never saved. Same key and 503 behaviour as polish. The "Summarise" button (sparkles icon, `TicketSummary`) sits below the message in `TicketDetail`.

## Error monitoring (Sentry, client and server)
### Client
- `@sentry/react` is initialised in `client/src/main.tsx` **only when `VITE_SENTRY_DSN` is set** (see `client/.env.example`), so dev, tests and CI send nothing. Never hard-code the DSN.
- Errors only: no tracing, replay or logs. SDK v11 has no `sendDefaultPii`; `dataCollection` is set to collect nothing extra (no user info, cookies, headers, bodies or query params).
- The app is wrapped in `Sentry.ErrorBoundary` with `ErrorFallback` (shadcn `Alert` + reload button).

### Server
- `@sentry/bun`, initialised in `server/src/instrument.ts` **only when `SENTRY_DSN` is set** (in `server/.env`; empty in `.env.example`), so the server runs fine without it. Never hard-code the DSN.
- It is loaded with `bun --preload ./src/instrument.ts` (the `dev` and `start` scripts), Bun's equivalent of Node's `--import instrument.js`, so it runs before any other module. The e2e API starts with plain `bun src/index.ts`, so it sends nothing.
- Errors only: no tracing, profiling or logs. `dataCollection` collects nothing and `beforeSend` drops `event.request` and `event.user` (no emails, ticket text, bodies, headers or cookies).
- Bun can't auto-patch Express, so `Sentry.setupExpressErrorHandler(app)` (after all routes in `server/src/index.ts`) is what captures route errors.

## Deployment (Railway)
- **One service, one origin.** The root `Dockerfile` builds a single image: `prisma generate`, the client build (`client/dist`), then runs the server (`bun --preload ./src/instrument.ts src/index.ts`). In production (`NODE_ENV=production`) `server/src/index.ts` serves `client/dist` and falls back to `index.html` for client routes (never for `/api`). No CORS is needed or added. The pg-boss worker runs inside this same process; keep 1 replica at first.
- **`railway.json`:** Dockerfile build, healthcheck `/api/health`, and the pre-deploy command `bunx --bun prisma migrate deploy` (the only migration command in production). **Never** run `migrate reset`, `migrate dev`, `db push`, `bun run test:db` or the `seed:tickets` / `seed:replies` demo scripts against a deployed database. Create the first admin once with `bun run seed` (temporary `SEED_ADMIN_*` variables, remove the password afterwards). Back up the database before the first migration.
- **Variables (names only):** runtime `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (public https origin), `TRUSTED_ORIGINS` (same origin; the default is localhost, so sign-in fails without it), `NODE_ENV=production` (secure cookies and rate limiting), `TRUST_PROXY_HEADERS=true`, `GOOGLE_GENERATIVE_AI_API_KEY`, `INBOUND_EMAIL_SECRET` (optional), `SENTRY_DSN`, `AUTO_RESOLVE_SHADOW_MODE` (leave unset or anything but `false` to stay in shadow mode; `false` makes AI auto-resolve live). Build time: `VITE_SENTRY_DSN` (declared as a Dockerfile `ARG`). `PORT` is set by Railway. Never set `API_PROXY_TARGET` or `E2E_*` there.
- `.dockerignore` keeps `.env*` (except the examples), `node_modules` and `e2e` out of the build context.

## Testing strategy
- **Default to component tests; E2E only when necessary.** Cover UI behaviour (rendering, loading/empty/error states, forms and validation, dialogs, role-dependent UI, labels) with component tests: they are fast and need no server or database. Don't duplicate in E2E what a component test already covers, and when a feature could be tested either way, write the component test.
- **E2E is for what component tests can't prove**, because it needs the real client, server and database together: session and cookie auth, authorization enforced by the server, database effects (soft delete, uniqueness, idempotency), server-only endpoints such as the inbound email webhook, and flows that span pages. Keep E2E suites small and focused on these happy paths and critical checks.
- **Don't keep an E2E test that a component test already covers.** Keep E2E only for what needs the real client, server and database, and always keep the server-side security tests (login/session, `/api/users` authorization, origin check, inbound-email webhook secret).
- The rules below on when to write or run tests still apply: write or run either kind only when I explicitly ask. This section only decides which kind to reach for.

## Component tests (Vitest + React Testing Library)
- **Run:** `cd client && bun run test` (single run, all tests) or `bun run test:watch` (re-runs on save while writing). One file: `cd client && bunx vitest run src/pages/UsersPage.test.tsx`. These are fast and need no server or database; they are separate from the Playwright E2E tests.
- **Where:** `<Component>.test.tsx` next to the component. Shared helpers are in `client/src/test/`: `setup.ts` (jest-dom matchers, cleanup, loaded by `vite.config.ts`) and `render.tsx` (`renderWithQuery`, wraps the component in a fresh `QueryClientProvider` with retries off). Add new shared helpers there; wrap routing in `MemoryRouter` inside the test when a component needs it.
- **Writing:** import `describe`, `it`, `expect`, `vi` from `vitest` (globals are off). Query like a user: `getByRole`, `getByLabelText`, `getByText`; use `findBy*` for async results and `queryBy*` to assert absence. Avoid `data-testid`, snapshots and testing implementation details. Mock the network with `vi.spyOn(axios, 'get')` (or `post`, etc.) and build errors with a real `AxiosError`; don't mock React Query itself. Restore mocks in `afterEach(() => vi.restoreAllMocks())`. Cover loading, success, empty and error states, plus role-dependent UI.
- **Executing:** run the relevant test file after writing or changing it and fix failures before reporting; show the results. Don't weaken a test to make it pass: report a real app bug instead.
- Same rule as E2E: write or run component tests only when I explicitly ask (see Testing strategy above for which kind to use).

## E2E testing (Playwright)
- Config: `playwright.config.ts` (root); tests go in `e2e/tests/`. Run `bun run test:e2e` (or `test:e2e:ui`) from the repo root. Chromium only; install with `bunx playwright install chromium`.
- **Separate database:** `e2e/.env.test` (gitignored; copy from `e2e/.env.test.example`) points `DATABASE_URL` at `helpdesk_test`. Playwright starts its own API (port 3100) and client (port 5183) with that env, so it never touches the dev database and can run next to the dev servers.
- Before the API starts, `server/prisma/e2e-setup.ts` (`cd server && bun run test:db`) runs `prisma migrate deploy`, truncates all tables and creates the test admin and agent from `E2E_*` env vars (credentials in `e2e/env.ts` as `testUsers`). It refuses any database not named `*_test` on localhost.
- Auth rate limiting is off outside production, so tests can log in repeatedly.
- Don't use `prisma migrate reset` for the test DB: Prisma blocks it when run by an AI agent without user consent.
- **Writing tests:** use the `e2e-test-writer` subagent (`.claude/agents/e2e-test-writer.md`) for all new or extended E2E tests, instead of writing specs inline. Give it the page, flow or feature and the roles to cover (admin, agent). It writes specs in `e2e/tests/`, runs `bun run test:e2e` and reports results. It does not change app code, `playwright.config.ts`, the DB setup script or `.env` files: if a test needs such a change (for example a `data-testid`), it reports back and the main session makes the change, then re-invokes it.
- Do NOT run E2E tests or add or update specs automatically. After code changes, run only typecheck and lint. Run E2E tests or use the e2e-test-writer subagent only when I explicitly ask.

## Documentation lookup (Context7)
Always use the Context7 MCP server to fetch current documentation before writing or changing code that uses a library, framework, SDK, or CLI tool (React, Vite, Express, Prisma, Tailwind, React Router, Zod, Bun, Anthropic SDK, etc.). Do this even for well-known libraries, since training data may be out of date.
1. `resolve-library-id` to find the library.
2. `query-docs` to get the relevant docs.

Skip it for general programming concepts or code that doesn't depend on a library API.

## Conventions
- The server uses TypeScript strict mode.
- **Shared validation:** schemas used by both client and server (e.g. `createUserSchema`) live in `core/src/` and are imported from `@helpdesk/core`; don't redefine them on either side. Add `"@helpdesk/core": "workspace:*"` to a workspace that needs it. Typecheck with `cd core && bun run typecheck`.
- **Express 5 async handlers:** don't wrap async route handlers or middleware in `try/catch` just to call `next(error)`. Express 5 forwards rejected promises to the error handler automatically. Only use `try/catch` when you need to do something on failure (e.g. clean up, as in the create-user handler).
- Follow `implementation-plan.md` phase by phase. Finish a phase, then stop for the user's approval before starting the next.
- Keep `tech-stack.md` and `project-scope.md` in sync if a technology or scope decision changes.
- Don't leave dev servers running in the background unless asked.
